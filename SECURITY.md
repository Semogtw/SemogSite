# Security

## Protected assets

The platform must protect:

- private repository names, URLs, roles and target lifecycle state;
- branches, observations, recommendations, blockers, evidence and session history;
- sync-run warnings, ETags, rate-limit state and provider timestamps;
- audit before/after snapshots and correlation IDs;
- authentication tokens, password hashes, CSRF secrets and GitHub tokens;
- database and backup files;
- unpublished drafts and internal project summaries;
- imported GitHub/Notion content that may contain untrusted instructions.

## Trust boundaries

1. anonymous browser → public web/API;
2. authenticated owner browser → DevOS/private server functions;
3. server functions → domain services and local storage adapters;
4. read-only GitHub client → structurally validated provider observations;
5. external documents → untrusted data ingestion;
6. future ChatGPT client → authenticated MCP tools.

## Authentication controls

The local Node/SQLite adapter:

- denies access when auth configuration is missing or invalid;
- stores a salted PBKDF2-SHA256 password hash;
- persists only digests of random session tokens;
- enforces 14-day absolute expiry and explicit revocation;
- transactionally revokes sessions after password-hash rotation;
- uses `HttpOnly`, `SameSite=Lax`, path `/` cookies and `Secure` in production;
- binds a readable CSRF token to the server-side session;
- rejects logout and private mutations with invalid CSRF;
- returns generic login failures and rate-limits attempts;
- resolves the current owner again in every private data server function.

The in-memory limiter is a single-process baseline. Multi-instance deployment requires a shared adapter.

## Operational mutation controls

Every current private write follows the same baseline:

- owner session and CSRF are revalidated server-side;
- actor, IDs and timestamps are generated by the server;
- reason and explicit confirmation are mandatory for sensitive changes;
- domain services normalize and validate before persistence;
- optimistic state checks reject stale browser snapshots;
- entity mutation and append-only audit insertion share one transaction;
- audit failure rolls back the entity mutation;
- UI success is shown only after a committed response and route invalidation.

Current audited repository actions are deliberately local:

- target registration;
- target pause/reactivation;
- branch-recommendation acceptance.

None of them sends a GitHub request.

### Target registration

The browser supplies project ID, canonical `owner/name`, expected default branch, canonical role, reason and confirmation. It never supplies a token or arbitrary URL. The domain generates a credential-free HTTPS GitHub URL. The database rechecks project existence and case-insensitive duplicate identity inside an immediate transaction.

New targets are private/manual and are not described as provider-verified until a read succeeds.

### Target lifecycle

Pause/reactivation updates only `sync_enabled` and `updated_at`. The expected flag and timestamp must still match. Historical observations, recommendations, active branch and repository identity remain unchanged.

### Branch decisions

The browser sends an immutable recommendation ID and expected current active branch. It does not supply authoritative recommendation branch text. The server reloads the latest recommendation, rejects stale or unavailable evidence, treats the default branch as the effective state when `active_branch` is null, and updates only `active_branch`/`updated_at` with the audit event in one transaction.

These services are prerequisites for future MCP writes. MCP must call the same domain services and cannot bypass confirmation, concurrency or audit rules.

## GitHub read-only integration

The provider adapter is read-only by construction:

- only repository metadata, branch listing and commit observation GET endpoints exist;
- there is no generic arbitrary-request method;
- API version and media type are explicit;
- owner, repository and ref path segments are encoded;
- responses are structurally validated before entering the domain;
- canonical identity, default branch and credential-free HTTPS URL are validated again at the provider boundary;
- branch scans are bounded and sequential;
- commit messages, README text, issues, PR bodies and other instruction-bearing content are not imported;
- authorization headers and raw response bodies are never persisted or logged;
- ETags and normalized rate-limit state may be persisted privately;
- a rate-limit response stops later commit reads for the current target;
- unexpected provider errors are contained per repository;
- valid partial evidence is retained while the parent run is marked `partial`;
- synchronization never writes `active_branch`, role, lifecycle status, `sync_enabled`, project progress, stage state or publication state.

Use a fine-grained token with the smallest repository selection possible and only Metadata read plus Contents read. `SEMOGTW_GITHUB_TOKEN` is read server-side, remains empty in `.env.example`, and must never enter HTML, browser fields, logs, database records or audit snapshots.

## Sync-run compatibility

Migration `0004_github_sync_runs.sql` extends the legacy run table additively. New runs populate both legacy and extended counters. This prevents a partially migrated runtime from silently recording misleading status.

Security-relevant invariants:

- a run cannot start without required legacy fields such as `trigger`;
- partial provider evidence cannot be reported as success;
- failed targets are counted and normalized;
- no token or raw provider body is stored in `metadata_json` or warnings;
- backups and restoration checks require all migrations through `0004`.

## Public/private isolation

Public routes and endpoints:

- use dedicated public query/serializer paths;
- construct DTOs from explicit allowlists;
- never spread private entities and remove fields afterward;
- never use private records as editorial fallback;
- omit records lacking approved public summaries;
- mark unknown/unpublished dynamic routes `noindex`;
- exclude private/unlisted content from sitemap and structured data.

Repository targets, names, URLs, roles, branches, observations, recommendations, decisions and sync runs are never public DTO fields.

Static gates cover public route/API source, assets, token/private-field markers, upstream identity and forbidden domain imports. Runtime HTML, loader payloads, metadata, sitemap and host caches still require browser/build verification.

## Private response caching

`/api/v1/private/*` applies before authentication:

```text
Cache-Control: no-store, private
Pragma: no-cache
```

Private TanStack loaders use route and server-function authorization. Host-specific CDN/cache behavior must be verified on the selected deployment.

## Prompt injection and imported content

External text is data, not instruction. Importers must preserve origin, sanitize content, cap size/types, never execute embedded commands, never put secrets into prompts and keep tool/system instructions separate.

The current GitHub phase intentionally avoids instruction-bearing bodies and stores only normalized metadata/head evidence.

## Logging

Allowed structured fields:

- correlation ID;
- route/tool name;
- sanitized actor ID;
- duration/result;
- integration and normalized rate-limit state;
- sanitized error code.

Never log request bodies, cookies, raw tokens, passwords, complete private URLs, audit snapshots, provider response bodies or private source content.

## Secrets and backups

Use runtime secret storage. `.env`, `.dev.vars`, database files, snapshots, backups and local worktrees are ignored. Example secret fields remain empty.

Backup commands:

- operate only on explicit local paths;
- refuse overwrite;
- use SQLite online backup;
- verify integrity, foreign keys and all migrations through `0004`;
- delete only a newly created invalid destination;
- never upload, encrypt, rotate or commit automatically.

The owner is responsible for encryption, filesystem permissions, off-device copies and retention. Backups contain private operational data, observations, decisions, audit evidence and authentication digests.

## Publication preflight

Block public deployment when scanners find:

- private repository names/URLs;
- branch, recommendation, target or sync-run markers;
- token/key patterns;
- private records in anonymous fixtures;
- unapproved publications;
- upstream personal content or template branding.

## Known limitations

- dependency installation, typecheck and production build have not run in this connector-only environment;
- browser-level confidentiality, cookie, cache and Operations behavior are not yet observed;
- live GitHub token permissions/provider behavior are not yet exercised from the app runtime;
- the in-memory limiter is not distributed;
- production host composition, CSP and deployment headers remain unselected;
- backup encryption and retention are operational responsibilities;
- no public deployment is authorized.
